MOBA Warmup

"Aim Lab for MOBAs" — mechanical and decision training built for the gaps in your game day.

Owner Roi (solo dev) Started 2026-06-01 Current build v1.5 WebGL Platform Browser → Overwolf (v2) Game League of Legends

01 Vision

Long-term positioning: "Aim Lab for MOBAs" — a training suite for every mechanical and decision skill in the game.

v1 positioning: "The last-hit drill that doesn't take you out of queue."

MOBA Warmup is a suite of short drills, playable in browser and via Overwolf overlay, for practicing the most important mechanical and decision-making skills of each MOBA role — without entering a full game. Every drill fits inside the dead time of the League of Legends game cycle: queue, champ select, loading screen.

01b IP Compliance & Build Split Foundational

Rule of thumb: anything that names Riot IP (Drake, Baron, Herald, Smite, champion names/archetypes) or reads the live client is legitimate only in the Overwolf build, where it operates as coaching over Riot's licensed API. The public standalone must be a fully generic skill trainer.

The product ships as two builds from one Unity project, split at compile time by the MW_OVERWOLF scripting define:

BuildDefineContentsWhy
Standalone (itch / WebGL) — none — Last Hit, ADC Kite, Loading Frenzy only. Zero Riot IP. Public product with no Riot API relationship → must not use Riot trademarks or client data.
Overwolf MW_OVERWOLF + Jungle, Support (and the live-client features: Mindset, Pick Advisor). Coaching over the licensed OW/Riot API → naming real champions/objectives is legitimate here.

Safety default: absence of the define yields the clean standalone, so an accidental or default build can never leak Riot IP. The Overwolf build must explicitly opt in. Build entry points (batchmode CLI): MOBAWarmupBuild.BuildWebGLStandalone and BuildWebGLOverwolf; the define is injected per-build via BuildPlayerOptions.extraScriptingDefines.

Versioning (since 0.9.0) — single source of truth is Unity's bundleVersion; 0.9.x covers everything up to the public launch, with 1.0.0 reserved for it. Every build stamps Resources/build_info.json (version, commit, timestamp, flavor) before the player is built, read back at runtime by Core.BuildInfo and shown dimly in the main menu's bottom-right corner as v0.9.0 · <sha>. That corner exists to catch a stale build — a cached itch upload or an un-repackaged Overwolf folder is otherwise indistinguishable from the new one, which is the easiest way to sign off on a change that never loaded. Zips are named MOBAWarmup-v<version>-<flavor>-<sha>.zip. Full detail in docs/builds-y-versionado.md.

The split is enforced in code at three surfaces, all gated with #if MW_OVERWOLF: the build scene list (MOBAWarmupBuild), and the two menus that list drills (DrillMapSelector, ChampSelectLanding).

Open cleanup tracks (post-Tier 1): Track B — strip the Jungle/Support script string literals from the standalone binary (dead code today, unreachable but present). Track C — replace the bundled Riot art with original art. First pass done: the loadout item icons and the role glyphs are now generated from original 3D icon models (Synty POLYGON Icons) instead of Data Dragon / Community Dragon, and the Riot PNGs were deleted. One mapping drives both outputs, so the icon that spins in the drill selector and the flat one in the HUD are the same artwork — see IconArtTool (MOBAWarmup/Icons ▸ Rebuild Catalog + Bake Sprites, batchmode-safe). Second pass: the drill-selector background, the ward and objective markers, the engage/peel glyphs and the ward trinkets are original art, and the Jungle minimap background is now an original 9x9 game board instead of the Summoner's Rift layout (scripts/gen_minimap_jungle.py → SVG → Inkscape, so it rebuilds from source with no AI credits). The board keeps the genre's topology — opposite-corner bases, three lanes, a diagonal river splitting ally from enemy, one buff per quadrant — because that is common to every MOBA and is what the drill trains you to read; what diverges is the expression: straight tile runs instead of curved lanes, a stepped river instead of a meander, a strict orthogonal grid. Decision-point coordinates snap to cell centres and are exactly 180°-symmetric about the board's centre. Still pending: 4 of the 8 dragon tokens, baron/riftherald, and summoner-smite — all awaiting painted art, all Overwolf-only surfaces.

Public-facing copy (itch page, store listings) removes all Riot trademarks, tags, and any head-to-head comparison against Riot's own Practice Tool. See docs/00_IMPORTANTE/itch-description.md.

04 Game Loops

Micro loop (within a session)

open tab → drill auto-starts → wave in ~3s → kill minions → stats overlay → replay

Macro loop (across queues)

open LoL queue → MOBA Warmup tab → drill while waiting
   → queue pops → auto-pause on tab switch → play game
   → game ends → more queue? → repeat

Progression loop (post-v1)

play game → OW captures performance data → seeds next drill session
   → session targets your real weaknesses → repeat until improvement

06 Mode A — Last Hit Done

The wedge product. One wave of 6 minions per side, auto-attack only, lane balanced. Validates the core hypothesis: players will use dead time to practice CS if friction is near zero.

Implemented mechanics

  • Click-to-move (right-click) + stop command (S key)
  • Auto-attack state machine: windup → damage → recovery; movement cancel
  • Attack-move (A key) — targets nearest enemy in range
  • Target priority rules (LoL rules 2 and 3)
  • HP bar color shift when one-shotable
  • Last-hit indicator: a ▼ marker appears over a minion the moment it enters one-shot range — a coaching cue toggleable in Options (CoachingPrefs, PlayerPrefs, default ON). Turning it off is the hardcore mode: no last-hit assistance at all.
  • Click indicator visual on right-click
  • Auto-pause on focus loss
  • LastHitTracker: CS hits, missed last-hits, wasted autos

Minion AI — LoL-accurate behavior

  • Stand and fight: minions plant in place when in attack range — NavMeshAgent RVO avoidance is halted (isStopped = true) so the agent doesn't drift while attacking. No separation forces during combat.
  • Attack cadence: melee 0.625 AS (~1.6s cycle), caster 0.667 AS (~1.5s cycle), matching LoL's visible windup + recovery. At 1.25 AS the cycle was 0.8s — attacks spammed with no perceptible gap.
  • March de-sync: per-minion speed jitter (±5%) + gentle lateral sine drift breaks the locked-step look without making minions look drunk. Values tuned against real LoL footage.
  • Reaction delay: on target death, each minion waits a random 0–0.25s before re-acquiring — staggers the "all robots turn simultaneously" look.
  • Move speed: 2.2 u/s (was 3.3) — matches the visual weight of real LoL minions marching down the lane.

Validation status

Cold load: 6.02s on broadband was measured on the ~12 MB build. The current build is ~48 MB (3D asset pass) — cold load must be re-measured; the <8s wedge constraint is at risk and no longer verified.

Validating: does Roi open it voluntarily across 10 consecutive queues? (The single most important metric for v1.)

07 ADC Kite Mode Done

Mode A + one add-on: an invulnerable enemy bot ADC that harasses. The skill trained is the fundamental ADC loop: auto → step → auto → step. The windup-cancel mechanic already in Mode A is exactly this — no new player-side mechanics needed.

The bot (EnemyBotADC)

  • Invulnerable. Minions ignore it. Player cannot target it.
  • Maintains band distance (~65–92% of its attack range) from player.
  • Telegraphed windup (body stretch + white tint, ~0.5s) before firing.
  • Projectile travels to the player's position at fire time — moving = dodge.
  • Respawns at the start of each new minion wave (WaveSpawner.OnWaveSpawned event) — the bot resets alongside the minions so pressure never stops between waves.

OW integration

Auto-launches when champ_select.position = 'adc'. Bot attack speed calibrated to the actual champion's base AS.

08 Loading Frenzy Active · v1

An endless arena drill — not the original multi-wave concept. The player stands at the center of a circular hex-tile floor while minions stream in from the four corners and home toward them. There are no wave boundaries and no end screen: the loop runs until the player clicks Main menu. It fills the loading-screen window (and any other dead time) with a tight, high-intensity execution loop.

The twist: the minions don't hurt you — the floor does. Enemy damage is 0; the real threat is the collapsing hex floor underneath you. So the drill layers two skills at once — last-hit / Q execution while constantly repositioning off the tiles that are about to drop. A 5s loadout picker (item stacks) opens the drill, freezing gameplay during its countdown.

Arena & spawns

ComponentRole

Combat loop — Q skillshot + autos

The player fires a Q line skillshot (~65 damage, range 11, projectile speed 30) alongside frenzy-tuned auto-attacks (attack speed 2.5, 0.05s windup). The Q runs on a short cooldown (~0.8s) that refunds 0.4s on a hit — accuracy literally buys you a faster cast rhythm, which is the core skill expression of the mode.

Progression — boost stacks

Every 10 lasthits grants a PlayerBoost stack (move speed + Q cooldown reduction only — no damage/power, per the 2026-07 balance pass), applied live. Keeps an endless run escalating in tempo without a meta-progression layer or a flooded screen at frenzy speeds. LastHitFeedbacks is also retuned for the mode (streak capped at 4, halved shake/ring bonuses) so the 20+ streaks the frenzy produces don't blow out the camera.

09 Jungle Mode Active · v1 Overwolf build only

The first hybrid decision + execution mode. Junglers don't fail because of bad aim — they fail because they misread the map or execute the right decision at the wrong time. This mode trains exactly those two layers.

Reading phase — animated script on the minimap

The scenario is shown, not read. Instead of a static wall of text, each scenario plays an ordered list of ScenarioBeats on the minimap: every beat reveals one caption line synced to a staged move — the enemy jungler walks in or backs (MapActor), the objective node pulses, a lane flashes its win/loss colour. A scenario with no authored script falls back to the legacy text panel, so beats roll out scenario-by-scenario. Decision points are sized by priority (Baron/Dragon large → buffs medium → scuttle small) so the map reads at a glance.

Decision phase — drag & drop on minimap

The player drags a chess-piece token (their champion) to the zone they want to prioritize on a 2D Canvas minimap. Deciding IS moving — the same spatial gesture as in real LoL. An enemy jungler ghost moves autonomously across the map; the player reads its position to reason about timing.

Execution phase — smite the monster

When the correct decision has an execution layer, the player smites a jungle objective whose HP descends through red → yellow → green zones (green = smite now). The objective is a MonsterType (Drake, Baron, Herald, buffs, scuttle…) driving its max HP and scale, so the smite window opens later for bigger targets — variety + difficulty instead of one fixed sphere. Models are placeholder capsules mounted under an ObjectiveAnchor (swappable for real models via a prefab slot). Steal scenarios spawn enemyContestCount enemy capsules around the pit so the player reads how many are contesting.

Feedback distinguishes why a round failed — OBJECTIVE LOST (the objective timer expired) vs TIMEOUT (no decision in time) vs INCORRECT — with a colour-flash + punch on the result card.

10 ★ Game Mindset New · v2

Core insight: Players already know what to do mechanically. What's hardest — and least coached — is the mental frame: what to focus on, when to shift, and how to recalibrate when things go wrong.

Philosophy

Every card answers one question: what does YOUR champion do, in YOUR situation, to maximize YOUR individual impact? This is solo queue coaching — the team doesn't exist as a controllable variable.

How it works

GAME MINDSET runs silently in the background during game_flow = InProgress. It monitors OW events and surfaces a single contextual mindset card when a meaningful game state change is detected. Maximum 5–6 cards per game. Scarcity is the feature.

Content system

Cards are stored in cards-db.json, indexed by [trigger][role][archetype][phase][state]. Lookup uses a 5-level fallback chain to gracefully handle missing combinations. Content generated by LLM from editorial rules, validated by Roi.

56 cards in Batch 01. Full coverage target: ~300 unique cards across all combinations.

⚠️ Compliance guardrail — the line that decides Riot/Overwolf approval: cards convey mentality, never live tactical intel. Live game state (gold diff, objective timers, tower events) only routes to a pre-authored static string — it is never rendered to the player. The MindsetCard type has no dynamic/interpolated fields, and that is the compliance lock: never add one. The riskiest triggers to author for are the objective windows (Baron/Drake) — a card must say "a big objective's coming, don't force it" (mental), never "set up vision / group mid" (tactical instruction). Full rules + prohibited/allowed examples: mindset/CARDS_AUTHORING_GUIDELINES.md.

10b ★ ChampSelect Pick Advisor New · v2

Core insight: Counter-pick sites give you a champion and a win-rate. They don't tell you why — and the "why" is the part that actually transfers to the game. Pick Advisor leads with the mechanic.

How it works

During champ select the app reads the live draft (LCU /lol-champ-select/v1/session). Each time an enemy locks a champion, it surfaces up to 3 suggested picks for your role, each with a one-line mechanical reason — "Morgana E (Black Shield) blocks the hook, your carry stays safe." Banned champions and ally picks are excluded automatically.

Threat prioritisation

When multiple enemies have locked, the panel shows counters to the highest-priority threat: your direct lane opponent first, then the jungler (affects everyone), then anyone else. Bot lane is treated as one matchup — an ADC is offered support-role counters and vice versa.

Mode 2 — filter by mechanic

The player can also filter by the tool they want: Spell Shield · Disengage · Poke · Guaranteed CC · True Damage… The advisor returns the counters in the matchup that provide that specific mechanic.

CounterDB

Hand-curated JSON (docs/counter_db.json, ~68 top champions), keyed by enemy champion. Each counter entry carries roles, a reason, a mechanic_tag, and a strength (hard / soft / situational). The enemy id→name map comes from the LCU champion-summary — no API key, no latency. Per-role coverage is complete — every champion played across two lanes now has counters authored for each lane (no fallback gaps), and no primary lane is left with fewer than two options.

Item Advisor Spec

Sibling module (spec'd, not yet built): after you lock, answer "what situational items beat this enemy comp, and when does each threat spike?" It reuses the Pick Advisor's poller, snapshot and overlay, and joins on the threat_tags already curated in counter_db.json — keyed by itemizable threat category (antiheal, CC, burst, auto-attacker…) rather than per-champion builds, so data upkeep stays small. Output: ranked situational items (filtered to your class) + an early / mid / late threat timeline. See champselect-item-advisor-spec.md.

Implementation status

End-to-end working ✅ — standalone TypeScript engine in pickadvisor/ (enemy-pick detection + CounterDB query + threat ranking + Mode-2 filter + live re-evaluation), 33 tests green and the full curated DB validated structurally. The OW background service polls /lol-champ-select/v1/session through the draft and forwards the raw session + champ map; a transparent topmost overlay window (overwolf-app/overlay/) runs the engine (bundled to browser JS via esbuild) and renders the 3 suggestion cards (with Data Dragon champion portraits) + Mode-2 filter chips. Suggestions are role-pure — a support is only offered support picks. Verified against the curated DB in a browser preview. Pending: Item Advisor implementation; overlay positioning tuning. Mastery-crown indicator is deferred — the LCU does not expose enemy mastery during champ select.

10c ★ Clipo AI — Coach con Memoria New · Spec

Core insight: Un coach que no recuerda tus partidas anteriores no puede decirte si estás mejorando. Clipo tiene memoria persistente por rol y celebra el progreso con números reales — "Muriste 1 vez antes del minuto 10. Antes eran 4."

Qué es

Clipo es el Layer 2 de Game Mindset. Donde Layer 1 (cards estáticas) da coaching instantáneo en el momento, Clipo provee análisis contextual profundo impulsado por Claude API — con memoria acumulada de las últimas 20 partidas por rol. Los dos layers son complementarios: Layer 1 sigue siendo la respuesta rápida, Clipo añade el análisis profundo y el vínculo.

El nombre es un guiño a Clippy (el asistente de Office): aparece en el momento correcto, ofrece ayuda específica, puede cerrarse. A diferencia de Clippy, Clipo es directo, no molesta, y encarna la filosofía editorial del Game Mindset.

Sistema de Memoria (por rol)

Persistido en overwolf.settings (local, sin servidor). Separado por rol — los benchmarks y errores de Jungle no son comparables con ADC. Cada rol tiene su propio rolling window de 20 partidas.

ClipoMemory {
  player_name:   string
  games_by_role: Record<Role, GameRecord[]>  // max 20 por rol
  total_games:   number                        // global, todos los roles
}

Cada GameRecord almacena: KDA, muertes antes del min 10, CS/min, vision score, objetivos, y lo que Clipo identificó como punto ① y ✓ en esa partida.

Detección de Tendencias

El TrendAnalyzer compara la partida actual contra el promedio de las últimas 5 del mismo rol. Señal significativa: cambio >20% en cualquier métrica clave.

Tono Relacional

La celebración de mejoras siempre incluye el número exacto — nunca es genérica. "Muriste 1 vez antes del minuto 10. Antes eran 4. Eso es enorme." es correcto. "¡Mejoraste mucho!" está prohibido.

Clipo no menciona rachas de derrotas como contexto negativo. No compara con otros jugadores — solo con el historial propio. El análisis siempre va hacia adelante. Se dirige al jugador por su username de OW cuando hay contexto de vínculo.

09b Support Mode Active · v1 Overwolf build only

The fifth drill of the multi-role suite, and the second decision + execution hybrid after Jungle Mode. The support doesn't fail because of bad hook aim — they fail because they don't know when or where to control vision, and don't recognize engage windows before they close. This mode trains exactly those two layers.

Wedge: "Practice the support's key vision and engage decisions, calibrated by your champion and the state of the map — without entering a game."

Reading phase — full-map minimap

Unlike Jungle (one quadrant), Support shows the full map — the support needs global context for roam and vision decisions. The reading phase (5s, clock visible but not pressuring) surfaces: next-objective timer (Drake/Baron), ally wards (green) and visible enemy wards (red), the three lane states (↑/=/↓), last-seen position of enemy jungler and enemy support, and a resources panel (trinket pips 0/1/2 + control-ward icon). Everything legible in 5s — no scroll, no hover.

Decision phase — two token types on the minimap

The key difference from Jungle: instead of a single draggable piece, the player can have up to two token types — the player piece (roam/engage/peel) and the ward tokens (trinket and/or control ward). Each scenario activates only one type to keep the read clean. Decision timer: 8s; letting it expire counts as a wrong decision (time is part of the support's judgement too).

Execution phase — CC timing mini-game

Triggered only for Type C (engage window) scenarios where the decision was to engage — the support equivalent of Jungle's smite timing. A simplified 2D side strip (not 3D): your support on the left, the target ADC walking left toward a brush. An engage window (gold highlight) lights up when the target enters engageWindowEnd and closes past engageWindowStart; press the CC key (Q in v0) inside it. Feedback: HOOKED (in window) / MISSED WINDOW (too late) / OUT OF RANGE (too early), with a timing bar showing where you pressed. The window/range varies by archetype (long-reach engage vs short enchanter CC).

Champion archetypes

Scenario distribution and CC-timing parameters are calibrated by archetype: Engage (Thresh, Leona…) → Type C×3, E×2 · Enchanter (Lulu, Soraka…) → E×3, A×2 · Poke (Xerath, Lux…) → A×2, D×2 · Roam (Pyke, Bard…) → D×3, C×1 · Flex (Milio, Rakan…) → even. Fallback if OW gives no champion: Flex. Adaptive weights persist in PlayerPrefs (3 fails → +20%, 3 wins → −15%), seeded from last-game OW metrics (low vision score → +A/B, deaths "outplayed by enemy support" → +C/E, few roams → +D).

10d ★ Leaderboard Online Active · v1

v1 hook: el primer sistema social del juego. Cada drill ya produce métricas de precisión, pero eran locales e invisibles. El leaderboard les da visibilidad pública sin agregar mecánicas — presión competitiva + retención. Apuesta deliberada como gancho de v1 (única feature sumada al núcleo después del freeze del scope).

Identidad — fricción casi cero

v1 es WebGL en itch.io: no hay Overwolf, no hay auth. El jugador escribe su summoner name una sola vez (la primera vez que termina una sesión) y se guarda en PlayerPrefs (IndexedDB en WebGL). Internamente cada jugador tiene un UUID v4 persistido — esa es la clave; el nombre es solo display. Sin login, sin cookies. Si cierra el modal sin nombre, el score se sube igual como Anonymous.

Fairness — modo Ranked: el loadout (items) y los minions per row cambian la dificultad, así que el score del modo libre no es comparable entre jugadores. Por eso los dos boards se juegan solo vía el botón RANKED, que fuerza la config estándar (sin items, wave fija de 3/row) ignorando el loadout guardado. Lo que se lanza desde DRILLS es práctica y no rankea.

RANKED abre un selector de board — LAST HIT o LOADING FRENZY — con la regla de puntaje de cada uno a la vista. Antes entraba derecho a Last Hit, así que el board de Loading existía en RANKINGS pero no había forma de llegar a él desde el menú.

Cambio 2026-08-05: Loading Frenzy subía desde el juego normal, con el argumento de que ya estaba estandarizado (HP fijo, el slider no aplica). Era incompleto: las constantes de frenzy pisan windup y attack speed, pero NO la velocidad de movimiento, así que 3 Boots del menú daban +30% de velocidad en un drill donde moverse es todo el juego. Ahora rige el mismo criterio que Last Hit. El picker de 5 s del propio drill (CDR + move speed) sigue activo en ranked: el presupuesto de stacks es igual para todos, así que es decisión del jugador y no ventaja de config.

Ciclos de 30 días

Ventana rolling de 30 días, global por modo. Se crea sola cuando llega el primer score y no hay ciclo activo; al vencer (start + 30d) se archiva automáticamente y el siguiente score abre uno nuevo. El leaderboard muestra el mejor score del jugador dentro del ciclo activo (no promedio, no último — un score peor se ignora).

Arquitectura

El cliente no conoce el cycle_id (la ventana se archiva/recrea sola). Toda la lógica vive en 2 funciones RPC SECURITY DEFINER en Supabase:

  • submit_score(mode, uuid, name, primary, secondary) — resuelve/crea el ciclo activo + upsert "mejor score", atómico. Devuelve { cycle_id, is_record, rank }.
  • get_leaderboard(mode, limit) — top N del ciclo activo, ya rankeado (read-only).
CapaTecnología
BackendSupabase free tier — PostgreSQL + PostgREST. RLS: lectura pública, escritura solo vía las RPC. anon key pública por diseño.
Web públicaHTML/JS estático en Vercel (leaderboard/web), fetch directo a las RPC. Tabs Last Hit / Frenzy, ?mode=, ?cycle=.
Cliente UnityAssets/Scripts/Core/Online/ — ScoreSubmitter (singleton, POST + identidad), LeaderboardPanel (overlay Hextech top 50), LeaderboardConfig.

Flujo in-game

  • Botón RANKINGS en el menú principal → overlay con tabs, top 50, fila propia resaltada, campo para fijar el nombre.
  • El score se sube solo al terminar la sesión (volver al menú en Last Hit; muerte o salida en Frenzy). El ScoreSubmitter es DontDestroyOnLoad para que el POST sobreviva el cambio de escena.
  • Primera sesión sin nombre → al volver al menú se abre el panel para ingresarlo; si no, sube como Anonymous.
  • Toast "Estás #N en <modo>" (o "¡Nuevo récord!") al volver al menú.

13 Architecture Principles

  • Namespacing from day 1: MOBAWarmup.Core.* / MOBAWarmup.Drills.LastHit.* / MOBAWarmup.Drills.Jungle.* / MOBAWarmup.Mindset.*
  • Do NOT abstract IDrill or DrillRegistry yet. Refactor when the 2nd or 3rd drill justifies it.
  • Auto-pause (OnApplicationFocus) is a shared behavior, not a per-drill feature.
  • Each drill owns its own DrillContext singleton — marker pattern, not inheritance.
  • OW bridges are thin adapters — no business logic inside them.
